# Ops Dashboard v3.1 — Spec

Consolidates four owner directives (agent-status taxonomy, correctness law, sensing layer,
sovereignty refinement) plus two v3.0 follow-up findings into one formal scope, per the
orchestrator's acceptance message. This is the SPEC — a staged implementation plan follows in
`verify/V3.1-PLAN.md`. Nothing in this document is built yet; v3.0's scoped "done" state (a real,
shipped, tested fix — see `CLOSE-OUT.md`) is the floor this spec extends, not a placeholder it
replaces.

## 1. The 8-state agent-status taxonomy

Replaces v3.0's 6-state classifier (`live`/`building`/`verifying`/`done`/`stalled`/`idle`) with a
finer-grained 8-state model. Each state carries: a color, a narrative verb, and a shown
**evidence string** — the "why I think so" a novice needs to trust the classification (M2's
trust requirement, made explicit per-state rather than implicit).

| # | State | Color | Meaning | Evidence shown |
|---|---|---|---|---|
| 1 | WORKING | green pulse | in-flight/recent tool_use | "last tool call Ns ago: `<tool>`" |
| 2 | COMPOSING | green, no pulse | recent assistant text, no tool call (writing/thinking) | "composing a response, Ns ago" |
| 3 | WAITING | blue | tail indicates deliberate wait (build running, inbox poll) | "waiting on: `<what>`, since Ns ago" |
| 4 | DONE/RELEASED | dim, calm | completion/stand-down semantics in the tail, no unfinished work | "sign-off Nm ago: \"`<snippet>`\"" |
| 5 | STOPPED/KILLED | grey-red | terminal failure evidence (session-limit, idleReason:failed, API error) | "session ended: `<error class>`" |
| 6 | PAUSED | amber | a control.json pause honored | "paused via control at `<ts>` by `<actor>`" |
| 7 | POSSIBLY STUCK | red + age | quiet beyond threshold, tail is mid-task, no completion semantics | "quiet Nm, mid-task: `<last tool/text>`" |
| 8 | ORPHANED/PRESUMED DEAD | dark red | long-quiet + unfinished + no matching OS process + beyond a longer threshold | "no process match, quiet Nh — presumed dead" |

**Narrative verb per state** (not one generic template): "X is working on...", "X is composing a
report", "X is waiting on a build", "X finished its task", "X's session was killed by...", "X is
paused", "X may be stuck", "X was killed by a session limit" / "presumed dead". Thresholds
(stall/idle/orphan windows) configurable in Settings, same live-apply pattern as v3.0's existing
`feed.debounceMs` etc.

## 2. The correctness law (governs HOW the taxonomy is built, not a separate feature)

**Accuracy is the goal; determinism is the means, not a literal requirement to defend at the cost
of accuracy** (owner's own clarification — when accuracy and rule-simplicity conflict, add
evidence-reading, not more rigid rules). Concretely:

- **Pure function of evidence inputs.** Given the same transcript tail + mtimes + control.json
  state (+ spawn-meta context — see the corrected source list below), the classifier returns the
  same verdict, always. Unit-tested as a property (same fixture -> same result across N runs).
- **Hysteresis at thresholds.** A state does not flap at a boundary — crossing a threshold plus a
  grace margin is required before the displayed state changes (prevents a novice from seeing an
  agent flicker between WORKING and POSSIBLY STUCK on a slow tool call).
- **Fact vs. inference, always labeled.** The dashboard STATES observable facts ("last transcript
  write 9m ago", "final entry is an unfinished Bash call") and LABELS interpretations as such
  ("possibly stuck," never "stuck"; "presumed dead," never "dead"). DONE (with a real sign-off),
  STOPPED (with hard error evidence), and WORKING (in-flight write <Ns) may assert plainly — those
  are backed by direct evidence, not inferred. POSSIBLY STUCK and ORPHANED are inferences and are
  marked as such in the UI copy itself, not just internally.
- **No numeric probability scores** — labeled confidence (fact/inference), never a fake-precision
  percentage (owner's explicit ban — uncalibrated numbers are worse than a clear label).
- **Ground-truth sources — CORRECTED after a real Stage-1 audit, not the originally-assumed 4
  equally-weighted sources.** Full audit: `verify/META-JSON-AUDIT.md` (8,208 real files scanned,
  0 parse errors). Real findings that changed this section from the original directive:
  - **Real evidence, cross-checked**: transcript `.jsonl` tail (last ~2 entries), file mtimes, and
    `control.json` requests. When these disagree (e.g., a control.json pause request exists but
    the transcript tail looks actively mid-task), the conflict is surfaced in the evidence string,
    not arbitrated silently.
  - **`meta.json` is CONTEXT ONLY, not a cross-checkable status source.** Audited: zero of 8,208
    real files carry any status/completion/idleReason-shaped field, ever — it's static spawn-time
    metadata (agentType/description/model/team). Used for evidence-string context (a "spawn
    brief"), never for classification. This corrects the original directive's "meta.json ... may
    include authoritative status" assumption.
  - **"Process table" cross-check is SESSION-level, not per-subagent.** Audited: every real
    `taskKind` value is `"in_process_teammate"` — subagents share their orchestrator's OS process,
    no individual PID exists to check. Reinterpreted for ORPHANED detection at the session level
    (implemented in v3.1 Stage 4+, not Stage 1's per-agent evidence layer).
- **Document the contract.** README gets a "what this dashboard asserts vs. infers, and why you
  can trust each" section — the fact/inference distinction stated as a standing product promise,
  not just an implementation detail.

**Test matrix required:** one fixture transcript tail per state (8 fixtures) · a determinism
property test · boundary/hysteresis tests at every threshold · a source-conflict test (control.json
vs. transcript disagreement, asserted as a shown conflict, not a silent pick). Stage 1's own tests
(`test/agent-evidence.test.mjs`, 11 cases) already cover the evidence-gathering layer these consume.

## 3. The sensing layer (recognition depth — ranked above further visual polish, per the owner)

Deep-reads transcripts far beyond "last tool name + truncated summary." New recognizers, each with
real test fixtures (a genuine tool-output sample -> the parsed structure), living in
`lib/recognizers/` (new directory, one file per recognizer family, config-driven patterns so new
harness formats are addable without code changes):

- **File-touch recognition**: Edit/Write/Read targets, extracted as structured paths (not just the
  truncated tool-input summary already shown).
- **Command classification**: Bash verb families — test / build / lint / git / db / deploy —
  classified from the command string, config-driven regex families (editable in Settings, the
  "recognition engine is the moat, keep it configurable" directive).
- **Test-result parsing**: pass/fail/skip counts extracted from tool OUTPUT (not just that a test
  command ran) via regex families for vitest, jest, `node:test`, Playwright, pytest shapes —
  each family gets its own fixture (a real captured output block -> asserted counts).
- **Error recognition**: API errors, session-limit deaths, permission denials, tool errors —
  classified from transcript content, feeding directly into taxonomy state 5 (STOPPED/KILLED)'s
  evidence.
- **Token/spawn/ACK semantics**: token-usage fields already partially surfaced (agents table);
  extend to stage-ping/ACK detection in SendMessage-shaped tool calls, and `agent_spawned` events
  already emitted (v3.0) get a richer "spawned by / spawn brief" evidence string where derivable.
- **Event vocabulary expansion**: new feed `kind`s — `test-run`, `build`, `commit`, `tag`, `error`,
  `death`, `spawn`, `ack`, `stage`, `control`, `file-edit`, `gate-pass`/`gate-fail` — each with its
  own icon/color; Live Feed's project filter row gains a kind-filter row to match.
- **Red-flag auto-elevation**: a failed test count, a build error, a death, an error streak
  surfaces itself into the attention band (Overview) + narrative, automatically — never buried at
  normal feed scroll depth.
- **Cross-source event linking**: a commit shortly after a test-pass by the same agent renders as
  a linked "verified -> committed" chain (not two unrelated feed rows); a tag updates the relevant
  milestone card.
- **Proof required**: unit fixtures per recognizer (real captured output -> parsed structure,
  matching the correctness law's test-first discipline) + a live feed screenshot showing the
  enriched vocabulary rendered, not just parsed.

## 4. Sovereignty constraint carried forward (already satisfied in v3.0 — a constraint on HOW v3.1 is built, not new work)

Every v3.1 addition stays inside the three-tier contract README.md already documents: the
recognition engine, the 8-state classifier, and all new UI are self-owned core (zero new runtime
deps, `node:*` builtins only). No new external validator categories needed beyond what v3.0
already uses (Playwright/axe, verification-only). No new "optional compounding reader" tier work
is in scope for v3.1 unless separately directed — this spec is entirely self-owned-core work.

## 5. Two carried findings from v3.0, folded in as small, discrete v3.1 items

- **Control-tab first-screen spirit gap** (`verify/M9-first-screen.md`'s honest observation): when
  a project has no control-request history, ~450px of first-screen space sits empty. Fix: a
  compact "recent activity across your projects" strip fills that space when the SELECTED
  project's own history is empty — small, self-contained, does not depend on the taxonomy/sensing
  work above and can land independently.
- **Status-palette chroma/CVD follow-up** (`verify/M8-skill-stack.md`'s dataviz-validator
  finding): nudge `--live`/`--verifying` chroma so the existing status hues would ALSO clear a
  strict categorical-chart-legend bar, not just the current icon+text-paired usage. Independent,
  small, a design-token change plus a re-run of `dataviz`'s `validate_palette.js` as evidence.

## Acceptance bar for v3.1 (unchanged discipline from v3.0)

Evidence scripts first-class from the start — every claim behind a rerunnable `verify/*.mjs`
script from day one of implementation, not retrofitted at close. Fact/inference labeling is a
product promise, not an internal detail — user-facing copy reflects it. No numeric confidence
scores anywhere. Same reproducibility bar: the orchestrator's independent re-run is the actual
acceptance gate, not the builder's own report.
