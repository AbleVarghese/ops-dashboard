# Ops Dashboard v3.1 — Staged Implementation Plan

Six stages, each independently testable and evidence-backed before the next starts. Stages 1-2 are
a hard dependency chain (the taxonomy needs the evidence layer); 3-4 can run once 2 lands; 5 is
independent and can land any time. No stage is "done" without its own `verify/*.mjs` script and
`test/*.test.mjs` fixtures — per the acceptance-bar discipline, not retrofitted at the end.

## Sequencing decision (and why)

Stage 1 before Stage 2 is a hard dependency — the classifier is defined as "a pure function of
evidence inputs" (the correctness law), so the evidence-gathering has to exist and be tested FIRST,
independently, before the classification logic that consumes it. Building them together risks
conflating "did I read the right data" bugs with "did I classify the data correctly" bugs — exactly
the kind of compound failure `superpowers:systematic-debugging` and this project's own
zero-rework-discipline exist to prevent.

Stage 5 (the two small carried findings) has no dependency on the taxonomy work and is cheap — it
can land whenever there's a natural pause, including right now, without blocking or being blocked
by Stages 1-4.

## Starting now: Stage 1

Beginning with the real meta.json audit (read actual files on this machine before writing any
evidence-gathering code) — the correctness law explicitly requires knowing the real shape before
building around an assumed one.

### HANDOFF — what remains in Stage 4 (for the next session)

Per `verify/V3.1-SPEC.md` §3, the sensing layer is: recognizers → event vocabulary → auto-elevation →
cross-source linking → live wiring → proof. Only the first recognizer of five is done. In dependency
order (each is independently buildable/testable per the Stage-1-style discipline — evidence-gathering
proven correct BEFORE it's consumed):

1. **Remaining recognizers** (`lib/recognizers/*.mjs`, one file + one test file each, matching the
   `test-results.mjs` shape — a `FRAMEWORKS`/pattern array + a `recognizeX(text)` export):
   - **File-touch recognition** — classify which files an agent's tool_use entries touched (Read vs
     Edit vs Write vs Bash-that-touches-files) from the transcript tail already gathered by
     `lib/agent-evidence.mjs`'s `lastTranscriptActions()`. No new I/O — this consumes Stage 1's output.
   - **Command classification** — categorize Bash tool_use commands (build / test / git / install /
     destructive / other) for feed narration and red-flag detection (below).
   - **Error/death recognition** — the piece Stage 2's STOPPED/KILLED states are documented as
     depending on (`V3.1-PLAN.md` row 4's dependency note); detect crash signatures, uncaught
     exceptions, and process-death patterns in transcript tails.
   - **Token/spawn/ACK semantics** — recognize the spawn-acknowledgment and stage-ping protocol
     patterns this very campaign uses (see the `handoff-302b18c1.md` "ACK/stage-ping protocol" note)
     so the dashboard can surface them as first-class events, not raw text.
   - **Evidence bar for each**: a real captured fixture (from an actual transcript/output sample on
     this machine), never a reconstructed-from-memory string — this is now the established norm for
     this project (see the Stage-4a real-fixture precedent above), not a suggestion.
2. **Event vocabulary expansion** — 12 new feed `kind`s (named but not yet enumerated in this plan;
   derive the exact list from `verify/V3.1-SPEC.md` §3's "expanded event vocabulary" directive plus
   what the 4 new recognizers above naturally produce — e.g. `file_touch`, `command_run`, `test_result`
   (already producible from the built recognizer, not yet wired), `error_detected`, `process_died`,
   `ack_received`, `stage_ping`, etc.). Land this as a single reviewed list before wiring, so the feed
   schema doesn't grow ad hoc per recognizer.
3. **Red-flag auto-elevation** — rules that promote specific recognized events (e.g. `error_detected`
   with a fatal signature, `process_died` unexpectedly) to a higher-visibility feed treatment
   automatically, without a human needing to notice them in a scroll of normal activity.
4. **Cross-source linking** — correlate events across the evidence sources Stage 1 already gathers
   (transcript tail + meta.json + control.json + process table) so, e.g., a `test_result` event can be
   linked to the `command_run` that produced it, per the "correctness law"'s cross-checking directive.
5. **Live wiring + proof** — connect the recognizers into the actual feed pipeline (not just unit-tested
   in isolation), then a `verify/screenshots.mjs`-style live feed screenshot showing the enriched
   vocabulary rendering in the real UI — this is the Stage 4 acceptance bar per the plan's table
   ("a live feed screenshot showing the enriched event vocabulary"), not yet met.
